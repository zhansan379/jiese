# 实现计划：Claim 共识层 · 实体标注与受限关系 · 对话画像槽位

> 前置事实：知识库 6434 chunks（PG `chunks` 表含 tokens/embedding）、混合检索（BM25+bge-m3→RRF→bge-reranker 融合→阈值过滤）、意图树 + LLM 打分、SSE 流式生成（Qwen3-32B）、链路追踪（tracing.py）、账号体系（users/chat_sessions）、管理后台 4 Tab 模式。
> 三项功能互相独立，无硬依赖；均不引入新基础设施（只用 PG 表 + 现有 SiliconFlow API）。

---

## 功能一：Claim 共识层（约 2.5–3 天）

### 目标
把"几十位戒友复述的相同经验"从分散 chunk 聚合成**带支持度的经验点（Claim）**，使答案能输出"飞翔及数十位戒友均强调断念口诀需每日练习[3]"，而不是随机抽 5 段同义复读。

### 数据模型

```sql
CREATE TABLE claims (
    id SERIAL PRIMARY KEY,
    text TEXT NOT NULL,              -- 规范表述（簇内最完整的一条）
    centroid vector(1024),           -- 簇心向量（bge-m3）
    support_authors INT NOT NULL,    -- 去重作者数（共识度）
    support_chunks INT NOT NULL,     -- 支撑 chunk 数
    authors JSONB NOT NULL,          -- ["飞翔","禅行僧",...]
    books JSONB NOT NULL,            -- {"jwly": 12, "jzl": 8}
    enabled BOOLEAN DEFAULT TRUE,    -- 管理端可停用劣质簇
    created_at TIMESTAMPTZ DEFAULT now()
);
CREATE TABLE claim_evidence (
    claim_id INT REFERENCES claims(id) ON DELETE CASCADE,
    chunk_id TEXT REFERENCES chunks(id) ON DELETE CASCADE,
    PRIMARY KEY (claim_id, chunk_id)
);
CREATE INDEX idx_claim_evidence_chunk ON claim_evidence(chunk_id);
```

### 离线构建管线（scripts/build_claims.py，一次性 + 增量）

```
① 抽取：全量 chunk → LLM 抽取原子经验断言
   prompt（Qwen3-32B, temp 0.1）：从摘录中抽取 0~3 条"可被他人复述验证的经验断言"，
   输出 JSON [{claim: "..."}]，跳过纯案例叙述/纯闲聊
   （6434 chunks，并发 8 路，约 4.5M tokens / 1–2 小时 / 免费档额度内）
② 嵌入：对断言文本调 bge-m3（约 1.2 万条断言，3 分钟）
③ 聚簇：贪心质心聚类——按序取断言，与已有簇心余弦 ≥0.85 归入，否则新建簇
④ 落库：簇 → claims（text=簇内最长断言，authors=来源 chunk 作者去重，
   support_chunks=簇大小），成员写 claim_evidence
⑤ 过滤：support_chunks < 3 的簇不参与运行时（噪声），保留在库可人工复核
```

### 运行时接入（改 3 处）

1. **retriever.retrieve() 末尾**：对最终 top-k 的 chunk_id 批查 `claim_evidence`（一次 SQL `WHERE chunk_id = ANY($1)`），命中的 claim 聚合去重后返回 `citations` 附带字段 `claims: [{text, support_authors, authors}]`（Citation dataclass 加字段，SSE citations 事件自动携带）
2. **generator.generate()**：摘录组装时新增"共识信号"段——

   ```
   共识信号（可信度参考）：
   - 断念口诀需每日练习形成条件反射 —— 飞翔及 27 位戒友均强调（覆盖两本书 20 处）
   ```

   SYSTEM_PROMPT 增加第 8 条：*“摘录旁标注了共识信号时，可用『飞翔及数十位戒友均强调』等表述归纳该点，并保留对应 [n] 引用；无共识信号的经验按个别戒友经验表述。”*
3. **tracing**：event_stream 里把命中 claims 数写入 trace extra_data（链路追踪 Tab 可见共识命中）

### 管理端（AdminView 新 Tab「经验共识」）

- 表格：规范表述 / 支持作者数 / 书籍分布 / 启用开关 / 展开查看证据 chunk（点击复用现有跳原文链路）
- 操作：停用劣质簇、合并（把 A 的 evidence 并入 B 后停用 A）——先做停用，合并放二期

### 验收

- 抽 30 个高支持度簇人工审：规范表述通顺、成员同义（≥80% 通过率再放量）
- 评测：对 10 道已知高共识问题（断念/警惕/学习戒色文章），生成答案应含共识表述且引用正确
- 端到端：断念类提问的答案出现"飞翔及 N 位戒友"字样

## 功能二：实体标注 + 受限关系（约 2–2.5 天）

### 目标
① chunk 打实体标签（检索时按实体过滤/加权）；② 两种受限关系（方法—对治→问题、因素—导致→症状）供生成端引用"书中对治频遗的方法：固肾功、睡姿…"。

### 数据模型

```sql
CREATE TABLE terms (
    term TEXT PRIMARY KEY,
    type TEXT NOT NULL,          -- 症状 | 方法 | 因素 | 概念
    aliases JSONB DEFAULT '[]',  -- 同义：滑精/梦遗/失精
    enabled BOOLEAN DEFAULT TRUE
);
CREATE TABLE term_edges (
    id SERIAL PRIMARY KEY,
    src_term TEXT NOT NULL,      -- 方法/因素
    rel TEXT NOT NULL,           -- 对治 | 导致
    dst_term TEXT NOT NULL,      -- 问题/症状
    evidence JSONB DEFAULT '[]', -- [chunk_id,...]
    UNIQUE (src_term, rel, dst_term)
);
-- chunks 加列
ALTER TABLE chunks ADD COLUMN IF NOT EXISTS entities JSONB DEFAULT '{}';
-- 形如 {"症状":["频遗"],"方法":["固肾功"]}
```

### 术语表种子（scripts/seed_terms.py，半天人工校对）

来源三路合并：现有 `glossary.CUSTOM_WORDS`/`FAMILIES`、《戒为良药》140 章标题挖掘（"X问题/X破戒"模式）、TF-IDF 高权词。预期 200–400 词条，类型人工标注（表格 CSV 导入）。管理页「术语与关系」Tab 可增改（复用意图树 Tab 的表格模式）。

### 实体标注（构建期 + 运行时）

- `scripts/backfill_entities.py`：Aho-Corasick 风格多模式匹配（terms + aliases 展开为匹配字典，Python 纯 dict 实现足够），对全量 chunk 正文打标签写 `chunks.entities`；`build_kb.py` 分词后同步挂钩（新 chunk 自动打标）
- 启动时 Retriever 加载 `chunk_id → set(terms)` 到内存 dict（6434 条，几百 KB）

### 关系挖掘（scripts/mine_edges.py）

- **模式匹配为主**（免费、可控）：
  - 对治：`对治|克服|摆脱|彻底解决` 连接的 (方法, 问题) 对，方法词来自 terms[type=方法]
  - 导致：`导致|造成|引起` 连接的 (因素, 症状) 对
  - 章节标题强信号：标题含症状的章内出现的方法实体 → 对治边（如第 3 章频遗 → 固肾功）
- 证据：边记录来源 chunk_ids；`support` 低于 2 的边不进运行时
- 人工复核：管理 Tab 表格展示边（源→关系→目标 + 证据数 + 跳原文），可删除噪声边

### 运行时接入

1. **查询实体识别**：`retrieve()` 内对 query 做同字典匹配 → query_entities
2. **候选加权**（RRF 融合后、rerank 前）：候选 chunk 的 entities 与 query_entities 有交集 → RRF 分数 ×1.2（加成而非硬过滤，避免空集；交集为空不加成）
3. **关系增强生成**：query_entities 命中的 `对治` 边汇总为生成上下文新增段——

   ```
   书中对治频遗的方法清单：固肾功、睡前拉筋、控制睡前饮水（来源 [2][5]）
   ```

   generator SYSTEM_PROMPT 第 9 条：*“提供了方法清单时，可作为回答骨架优先展开，仍需引用 [n]。”*
4. **trace**：query_entities 与命中边写 extra_data

### 验收

- 标注抽查：30 个 chunk 实体标注人工准确率 ≥90%
- 边抽查：对治边 top50 人工准确率 ≥85%
- 端到端："频遗怎么办"的答案应出现方法清单骨架；"下面总是湿乎乎的"经查询词映射→阴囊潮湿→命中阴囊潮湿实体加成

## 功能三：对话画像槽位（约 1.5 天）

### 目标
多轮对话中自动累积用户画像（戒色天数/主诉症状/身份），注入改写与生成，实现"那脱发呢 → 已戒100天的学生党脱发还能恢复吗"级别的个性化。

### 数据模型

```sql
ALTER TABLE chat_sessions ADD COLUMN IF NOT EXISTS profile JSONB DEFAULT '{}';
-- 形如 {"days_quit": "100天", "symptoms": ["脱发","社恐"], "identity": "学生党"}
```

profile 挂在 **session** 上（游客按 device、登录按账号，与现有云同步一致）；后续可聚合到 users.profile 做跨会话画像（二期）。

### 槽位抽取（每轮一次轻量 LLM 调用）

```
prompt：从用户最新发言抽取画像槽位，未提及输出 null，
JSON：{"days_quit": "100天"|null, "symptoms_new": ["脱发"]|[], "identity": "学生党"|null}
max_tokens=100，temp 0
```

- **与检索并发执行**（asyncio.gather）：抽取不影响本轮查询构造（消除延迟），抽取结果**写入 profile 后从下一轮起影响改写**，本轮立即影响生成
- 合并规则：days_quit/identity 取最新非空；symptoms 取并集（上限 10 个）

### 注入点（2 处）

1. **生成阶段**（本轮即时生效）：system prompt 追加——

   ```
   用户背景（供个性化参考，不要复述）：戒色时长 100 天；曾提及症状：脱发、社恐；身份：学生党
   ```

   同时在意图路由命中 kb 节点时与 gen_prompt 叠加（顺序：意图风格 → 用户背景）
2. **改写阶段**（下一轮生效）：`rewrite_query` 的 prompt 注入 profile 摘要，使"那脱发呢"改写为"已戒 100 天的学生党脱发如何恢复"

### 与 memory.py 的边界（并行开发功能，需协调）

- memory = **对话内容摘要**（聊了什么）
- profile = **结构化槽位**（用户是谁）
- 两者独立注入、互不覆盖；注入顺序：memory 摘要 → profile 槽位 → 摘录

### trace / 展示

- trace extra_data 记录本轮 profile 增量；前端不做用户可见 UI（隐形个性化），链路追踪 Tab 详情里可见当前槽位

### 验收

- 三轮对话测试："我戒 100 天了" → "最近脱发厉害" → "还有救吗"，第三轮改写应含"100 天/脱发"
- 延迟：抽取并发化后首包延迟增加 <300ms
- 槽位持久化：重启服务、换设备登录后 profile 仍在（云同步）

## 实施顺序与工作量

| 阶段 | 内容 | 工期 | 理由 |
|---|---|---|---|
| **P1** | 对话画像槽位 | 1.5 天 | 最小独立、见效最快（每轮对话都受益）、与 memory.py 协调点需尽早确定 |
| **P2** | 实体标注 + 受限关系 | 2–2.5 天 | 建立术语表与 chunk 标注基建（标注脚本模式可复用），检索精度直接提升 |
| **P3** | Claim 共识层 | 2.5–3 天 | 差异化价值最大但依赖批量 LLM 抽取的调参，放最后有 P2 的基建与评测经验 |
| 收尾 | 评测集扩展 + 文档 | 0.5 天 | 共识表述检查、实体加成检查纳入 eval 脚本 |

**合计约 7–8 个工作日。**

## 全局风险与对策

| 风险 | 对策 |
|---|---|
| LLM 抽取噪声（Claim/槽位） | 温度 0 + JSON 容错解析 + 支持度/频率门槛 + 管理端人工停用 |
| 加成/注入过度导致答案武断 | 实体用加成非硬过滤；共识表述模板固定为"书中认为/戒友们强调"；system prompt 强调不下医学结论 |
| 与并行开发（memory/tracing）冲突 | 三项均只新增表与独立模块（claims.py / entities.py / profile.py），main.py 接触点最小化；每功能独立 commit |
| 批量抽取成本 | SiliconFlow 免费档 + 并发限速 + 断点续跑（抽取结果落库缓存） |

## 统一验收（每项完成后跑）

1. `scripts/eval_retrieval.py` MRR 不低于当前 0.841（检索层无回归）
2. 22+N 题评测：三项各自的端到端断言（共识表述 / 方法清单骨架 / 画像个性化改写）
3. 链路追踪可见新节点信息（claims 命中数 / query_entities / profile 增量）
4. 移动端管理页新 Tab 可用（复用本次响应式模式）
